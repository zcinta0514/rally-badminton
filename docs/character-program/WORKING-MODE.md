# 会话组织、模型分工与质量控制

更新：2026-11-11。用户要求由 Codex 规划长线任务组织，并按精细程度选用模型。用户口述 Astro／So，当前暂按本环境可用的 Astra／Sol 理解；不据此更改账号套餐或全局设置。

## 一个主聊天统筹，按任务调用工作代理

当前聊天作为长期项目入口：负责需求、路线、阶段计划、证据审查、整合和用户沟通。技术子任务在需要且获当前用户／项目指令授权的情况下，由专门的子代理执行；结果回到主聊天，不要求用户管理多个窗口。

不因项目持续时间长就主动建立多个用户聊天。只有用户明确要求创建新聊天时才使用创建聊天工具。阶段切换和上下文压缩也不自动意味着需要重开聊天。

当前环境最多 4 个并发代理，包含主代理。日常采用主代理＋1 个执行代理；只有工作确实独立时，增加只读研究／验收代理。不是每个小任务都需要多模型讨论，不为填满并发名额而拆分任务。

## 模型与推理强度

下表是用户偏好和本项目路由策略，不是所有模型的能力排名。每次执行前以当时工具暴露的可用模型与推理档位为准。

| 任务 | 模型／档位 | 主要交付 |
| --- | --- | --- |
| 人物／动画架构、骨骼与蒙皮难题、动捕重定向、运动连续性、反复失败的根因 | gpt-6-astra，ultra | 约束清楚的方案、精细实现或根因分析与反例 |
| 关键动作是否真正自然、触球和支撑关系、阶段质量复核 | gpt-6-astra，ultra | 对固定输入及帧序列独立复查，指出具体不合格时间点 |
| 常规实现、工具集成、已明确方案的修正、回归排查 | gpt-6.1-sol，high | 可复现修改和验证证据 |
| 截图采集、参考片段整理、初步图像检查、资产清单、跑已有检查 | gpt-6.1-sol，medium；复杂时 high | 截图／帧序列、检查记录、准确的问题位置 |
| 日常沟通、总控、证据整合 | 当前主聊天模型 | 对用户负责的最终结论和下一步 |

模型 ID 和 ultra 档位来自本轮运行环境的代理工具枚举；不能用一份静态文档保证未来所有账号或会话都可用。若指定模型不可用，记录错误与可用替代，不声称已经使用 Astra。对关键任务降档可能影响质量时向用户说明。

## 能自动做什么，不能承诺什么

- 当前代理工具支持在创建子代理时显式指定 model 和 reasoning_effort；不同模型不要求用户开多个聊天。
- 当前没有暴露直接改当前主聊天模型的工具。不声称主代理能随时自行变成另一个模型；需要改变主聊天选择时，由用户在可用界面操作。
- 需要切换已运行工作代理的模型／档位时，先保存工作与交接，再按新参数创建新的代理。继续给旧代理发消息不等于修改了它的模型。
- 本环境显式模型覆盖使用不继承完整历史的代理启动方式，需提供精简上下文包；不能既选择全历史继承又假定模型覆盖生效。
- 工具支持不等于本轮实际调用成功。本轮仅核对能力并建立策略，没有为了展示模型切换而空跑代理。
- 使用现有环境中已提供的模型能力；不接入额外付费 API，不购买额度，不承诺无限使用或任意时间无人值守连续运行。

依据：[OpenAI 官方子代理文档](https://learn.chatgpt.com/docs/agent-configuration/subagents)，2026-11-11 已打开核对；实际接口能力仍以当前运行环境为准。

## 每个工作单必须携带的上下文

1. 任务 ID 与一个明确交付物，例如“站稳／后退到位两种杀球保持自然”，而非“把人物做好”。
2. 精确 worktree、分支、基线提交、允许读写文件；正在被其他任务修改的文件。
3. REQUIREMENTS、STATUS、相关决策、输入视频／模型／帧序列的确切位置及版本。
4. 禁止事项：不付费、不改玩法判定、不擅自替换正式资产、不合并发布、不覆盖他人修改。
5. 验收场景、复现命令、失败处理和结果输出位置。
6. 指定模型与推理强度；返回实际能核实的运行信息，无法核实的字段标明未验证。

代理返回必须包含文件差异、证据、失败／局限和下一步，不能只返回“完成”。主代理检查实际文件与输出，不照抄子代理结论。

## 写入和视觉工具归属

- 同一文件／同一 Blender 场景／同一浏览器预览只能有一个当前操作者。
- 共享 worktree 时，只读检查可以并行；互相依赖的写入顺序执行。
- 相互独立且较大的代码实验分别建 worktree，并记录依赖；不让多个代理同时改 athlete.js、同一个 .blend 或正式 GLB。
- 参考筛选可与代码审计并行；使用同一个浏览器的视频播放、时间跳转和截图检查需串行或使用明确不同的页面。
- 关键审查者先看需求和原始证据，再看实现者说明，减少把作者自评当结论的偏差。

## 视觉与动作验收的特别规则

“截图检查”不一定是简单任务。截图采集和明显穿模初筛可用 Sol；专业动作是否连贯，必须看正常速度、关键帧序列和慢放，必要时交 Astra 复核。

不从一张好看的截图宣称动作自然。不把能读取视频页面等同于已完整观看视频；只取得关键帧时明确观察范围。模型无法实际读取证据时，应先补证据而非提高推理强度猜测。

每轮采用：实现 → 自动行为检查 → 正常速度／慢放检查 → 独立复核 → 修正 → 用户阶段预览。模型一致认为好看不代替用户体验与 iPhone 13 测试。

## 长期接续与用户操作

- 同一聊天可以跨多轮接续，但不把完整项目记忆只放在聊天上下文里。
- 每完成一个可检查结果、发生路线变化或准备暂停时，更新 STATUS、证据清单、决策和本地提交。
- 上下文压缩后先读文件再接续；不重复安装已验证工具，不重复询问预算与参考方向。
- 真正需要换聊天时，先记录精确目录、分支、提交、输入资产、运行服务、已知失败、下一个动作和授权范围；由用户明确要求新建或自己打开新聊天。旧执行者停止对相同文件写入。
- 一轮结束不表示项目会无限自行在后台继续。用户可在同一聊天发“继续人物项目，按 STATUS 推进”；已授权范围内无需重复确认每条命令。
- 不创建定时自动化来追踪这项具体项目的完成；长任务在当轮跟进并保存进度。
