## 1. 最高优先级与执行原则

1. **先重建完整打球过程，再完善人物外观细节。** 实现到位、触球、出球、随挥、制动、回位和下一拍准备之间的连续关系。
2. **以最终效果质量选择路线，不限制制作成本、时间、算力或工作量，允许重新建模。** 此项取代此前零额外付费的方案筛选约束；骨骼与动作优先、面部次要，具体消费和外部委托按当次授权执行。
3. **首先通过五组运动场景：发球、前场弓步、后场高远／杀球、平抽连续交换、击球后的制动和回位。** 面部、发丝、服装微纹理排在这些场景之后。
4. **触球高度、拍面方向、身体朝向、移动速度共同决定球路。** 同时纳入来球速度、挥拍速度和挥拍方向，区分卸力、借力与主动发力。
5. **手机采用“来球位置＋触球时机＋当前姿态”的情境化击球，不扩成八个球种按钮。** 保留少量稳定的战术意图入口，让玩家能在相同情境中选择不同打法。
6. **每次击球必须有合理的制动、恢复平衡和回位衔接。** 动画进入 recovery 阶段不等于完成战术回位，球落在界内也不等于打球系统完成。
7. **保留真实比例、自然的适度风格化。** 衣服自然贴合，不靠整体撑大遮盖穿插；球拍与握拍、脚底支撑必须一起验收。
8. **不把已有投入当作质量保证。** 现有骨骼数量、动作数量和模型形状不是不可更改的限制；替换之前保存已有成果和对照基线。
9. **在实际游戏中验收。** 正常速度观感、手机操作、球路可解释性与连续回合优先；数值检查辅助定位问题，不能代替视觉和玩法验收。
10. **制作期间持续提供侧边栏实际球场预览。** 源码或资产更新后重启快照服务，并核验浏览器实际加载内容；不得仅凭构建成功或刷新宣称预览已更新。

本文优先于旧日期人物计划中与本方案冲突的制作顺序。历史检查点继续作为可复现证据；用户后续明确指令优先。后续相关编码应对应下文任务编号及验收场景，避免脱离打球目标堆积外观细节或工具。

## 2. 当前做法与目标路线的差异

以下是 2026-09-30 调查时的对比，用于解释改动理由，不是持续更新的实现状态表。

| 环节 | 调查时的做法 | 目标 |
| --- | --- | --- |
| 动作来源 | 少量真实动捕与制作片段；现有动捕以高远、反手平抽为主 | 按完整回合采集，覆盖到位、击球、随挥、制动、回位及被动衔接 |
| 球路 | 主要按高远／吊球／杀球类别与目标落点反算，部分触球质量因素修正结果 | 由触球状态、挥拍方式和玩家意图共同产生，不保证命中瞄准落点 |
| 移动 | 已有位置控制、加减速、跳跃和动作适配 | 将支撑脚、朝向、速度、制动和下一步启动能力统一 |
| 回位 | 已有动作恢复阶段 | 增加真实恢复平衡、转向、重新启动和战术站位 |
| 人物 | 已有身体、服装、球拍与骨骼，动态表面尚有失败项 | 先通过运动压力测试，再完善外观；底模与骨架可按质量重做 |
| 衣物修形 | 主要随动作片段时间烘焙 | 覆盖动作混合、接地和触球适配后的最终姿态 |
| 手机操作 | 三个固定球种按钮 | 少量稳定意图入口，根据情境选择实际技术 |
| 联机 | 输入校验及协议围绕原有球种 | 同步新的意图、触球、动作与恢复状态，保持权威判定一致 |

保留有价值的基础：Three.js 运行时、动捕导入、连续过渡、脚底和拍头检查、预览、比赛与联机框架。旧候选的失败帧应成为回归样本；不能把持续修补旧候选作为拒绝新路线的理由。

## 3. 推荐制作与技术路线

**专项动作需求 → 专业动作参考与许可适用数据 → Blender 控制骨架、重定向与专项关键帧精修 → 共享击球和身体运动状态 → Three.js 最终姿态修形 → 实际比赛与手机验收。**

### 3.1 参考驱动制作为当前主线

- 按用户最新决定推进 [P1-3B](tasks/P1-3B.md)：新控制骨架／变形对照，短发球、前场弓步防守、后场击球三个完整小样，再扩展五组场景。面部与外观细节后置。
- 使用专业参考分析技术阶段、支撑、重心和发力节奏；公开视频可见性不足时标记未知，不把单目估计当三维实测。已有许可适用的 MultiSense 身体数据可以重定向，手指、球拍、触球与足地仍需专项制作和独立说明。
- Blender 制作控制器与导出变形骨架分离，检查 IK／FK、肩胛协同、前臂扭转、足跟／前掌滚动及手指握拍。可重做拓扑和权重；先以已有休止表面作 A/B 便于归因，不能把它当不可更改限制。
- 人工制作、参考分析、数据重定向分别标注。每段保留准备、启动、击球、随挥、制动、回位及下一拍；编排的触球事件不是传感器测量。
- 验收实际变形、穿插、支撑滑动、关节连续性、握拍、拍面／出球一致性和正常速度观感。旧失败阈值不为换路线而放宽；未测科学精度保持未测。
- [专项采集规格](MOTION-CAPTURE-SPEC.md)等资料保留为未来可选增强，不要求用户先找供应方或发邮件。采购、付费调用、外部委托、正式资产替换和发布仍按具体授权处理。

### 3.2 人物和服装服务于运动

- 先使用比例正确、便于编辑的运动员身体与简单运动服，检查肩、髋、膝、脚踝、前臂和握拍。
- 保留现有 CC0 底模作对照；按动态质量决定精修、局部重拓扑或更换成熟底模。Character Creator 可提供人物生产基础，不是必须采购的前置条件。
- 在 Blender 中完成游戏用拓扑、权重、专用控制绑定与姿态修形；制作控制器和导出变形骨架分离，按需求保留扭转、肩髋、足部与手指控制。
- 高精度母版与实时网格分开。身体、上衣、短裤、鞋、头发独立制作，保持统一比例与握拍接口。
- Tripo 仅作为外观参考或局部资产候选，不再把 Tripo 外观对比放在下一阶段最前面。
- 服装采用真实剪裁思路，Blender 或 Marvelous Designer 可辅助离线垂落与动态检查；最终整理为可控的实时网格。首版不以手机全身实时布料模拟作为稳定性前提。
- 面部、发丝、皮肤及布料微纹理在五组运动场景通过后完善，继续保持自然的适度风格化。

### 3.3 动作精修、选择与最终姿态修形

- 动捕进入 Blender 后处理比例差异、前臂轴向旋转、手指握拍、脚底支撑、收拍避让和动作间连续性。不能仅靠加密关键帧解决僵硬。
- 每段动作记录触球时刻、支撑窗口、触点范围、拍头轨迹、拍面方向、允许转向范围和恢复阶段。保留来源、修订版本与验收状态。
- 移动、急停、转向、回位采用基于姿态与目标轨迹的动作选择／匹配；击球使用明确的技术阶段和接触约束，不让任意混合破坏触球。
- 运行顺序固定为：动作选择与采样／混合 → 根部、朝向和足地适配 → 击球、握拍与球拍约束 → 辅助骨 → 最终姿态修形 → 渲染与表面检查。
- 从实际 Three.js 运行姿态采样，在 Blender 中制作身体和衣物局部修形，运行时由最终局部关节姿态驱动形态键。主要防穿插修形不能只随片段时钟播放。
- 修形插值有明确适用范围；未覆盖姿态记录为缺口并补样，不无界外推。先修动作和权重，再做局部形态修正。
- 收拍穿身通过随挥路径、躯干协同和恢复路径解决，不用撑大衣服、缩短球拍或放宽门槛遮掩。
- Blender 驱动器、约束和模拟不视为 GLB 自动携带的运行逻辑：应烘焙的轨道离线烘焙，姿态规则在运行时显式实现并对齐验证。

### 3.4 击球、球路与回位统一

统一行为流程：**表达意图 → 根据来球和姿态选择可行技术 → 身体与球拍完成挥拍 → 触球计算产生球路 → 随挥、制动、回位 → 下一拍准备。**

- 瞄准落点表示意图，不保证结果；可达触点、身体姿态、拍面、挥拍和来球速度共同限制实际出球。
- 完成发球、平抽、挡网、搓网、推球、挑球、杀球防守，并保留高远、吊球、杀球。发球独立处理；球种不能仅改名称或改变固定落点。
- 平抽、推球、挡网、挑球需要不同挥拍速度与方向；搓网要体现切向触球和近网飞行差异；杀球防守包含挡、抽、挑等在高速来球下的技术选择。
- 在共享逻辑中建立经参考数据校准的羽毛球空气阻力与出球模型，替换完全依赖抛物线和落点反算的做法。模型复杂度按实际球路证据决定，不凭空宣称物理完全真实。
- 每次击球后处理随挥、落地／制动、恢复平衡和再次启动能力；连续平抽采用紧凑恢复，允许合理衔接下一拍，不强制播放长回位动画。
- 回位目标结合己方击球、对手位置与可能回球区域，不固定冲向场地中心。只使用当前可观测或规则允许的信息，不预知对手未来输入。
- 推荐默认提供可被摇杆覆盖的回位辅助，允许抢网、留后场等选择；是否达到足够可控的手感以手机试玩决定。辅助不能瞬移、拉长肢体或忽略制动。

### 3.5 手机情境化击球

推荐交互原型：保留现有三个操作位置，改为稳定意图 **控制／进攻／高球**，配合方向拖动与释放时机。这是需试玩验证的原型，不是已证明最优的 UI。

| 来球与姿态情境 | 控制 | 进攻 | 高球 |
| --- | --- | --- | --- |
| 前场接近网口 | 放网；满足条件时搓网 | 推球或扑压 | 挑球 |
| 中场平快来球 | 挡球、卸力 | 平抽 | 防守起高 |
| 后场头顶来球 | 吊球 | 到位条件允许时杀球 | 高远球 |

- 实际技术由来球位置、触球时机、当前姿态和意图共同选择；相同情境仍允许不同战术。
- 搓网、推球等细分技术必须有可学习、可预测的触发方式，不能随机选择或突然改变按钮含义。
- 按下、拖动、释放的意义保持稳定；显示当前可行技术或触球风险，避免在接近边界时反复跳变。
- 不可行意图应有明确反馈或可预期的受限出球，不能偷偷转换成无代价的理想球。
- 新手辅助可扩大容错，但仍保留姿态与触球的因果关系。桌面调试输入与手机意图映射一致。

### 3.6 共享接口、联机与性能

- 共享比赛逻辑负责权威触球、球拍运动状态与球路，画面按同一状态呈现。不得从依赖渲染帧率的骨骼结果直接决定得分或出球。
- 规划输入意图、身体运动状态、触球事件和恢复状态接口；同一事件 ID 只触发一次击球，暂停、倒带、回放与不同渲染帧率下行为一致。
- 更新输入校验、状态快照、协议版本和兼容检查；不能只扩展动画目录而遗漏仍只接受旧三球种的联机入口。新旧协议不兼容时明确拒绝，保留旧模式独立可用。
- 新增角色资产清单与修形数据，记录候选 ID、骨架版本、来源许可、GLB、动作及验收关联；保留层级与绑定矩阵。
- 保留 Three.js。离线制作可以复杂，手机运行时仍需要针对双人比赛验证帧耗时、加载、内存和输入响应。
- 在目标手机、固定画质和可复现双人场景上冻结性能基线；在进入外观细节阶段前定义并验证帧率与输入延迟目标。桌面结果不能代替手机结果。
- 新行为先进入隔离的实验入口，默认正式角色和规则不由本计划落档直接替换；正式切换另行确认。

## 5. 验收方法与失败判据

### 5.1 视觉与玩法

- 在同一镜头、灯光、来球与输入条件下比较基线和候选，优先正常速度连续回合，再用慢放定位。
- 必须能从触点、拍面、朝向、移动和发力解释球路；不能每种姿态都输出同样理想落点。
- 支撑、发力、随挥、恢复自然；明显脚滑、关节翻转、皮肤塌陷、衣物鼓胀、握拍漂移和球拍穿身均不通过。
- 玩家应能预测意图输入的结果，主动控制回位方向；连续平抽不能被不必要的长动画锁住。
- AI 和玩家使用同一技术可行性与移动约束，不能由 AI 越过触点或恢复限制。

### 5.2 几何与运行一致性

- 检查真实导出 GLB，以及 Three.js 完成混合、足地和触球适配后的表面；骨骼代理无碰撞不能代替真实表面检查。
- 覆盖单动作、转换中间帧、连续打断、暂停倒带、两侧球场、不同触球高度及速度。
- 延续现有衣物采样超过 1 mm 穿插即失败的门槛；触球点误差目标不超过 1 cm，支撑窗口鞋底漂移目标不超过 5 mm。以上是工程验收目标，不是已达到的结果，采样通过不保证所有未采样姿态。
- 验证 Blender 与运行时修形一致；超出样本覆盖范围必须可诊断，不能以静态图通过代替动态检查。
- 验证固定模拟时步、低帧率渲染、回放、网络延迟与重复消息下无重复触球或判定分歧。
- 按改动运行必要测试和构建；通过后无新改动或失败不重复堆检查。每一阶段保留可追溯的资产和场景证据。
