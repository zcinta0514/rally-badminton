# 单人开发与 AI 对话接续流程

本项目采用轻量 GitHub Flow：**任务 → 独立分支 → 小步提交 → Draft PR → 验收 → 合并并核验发布**。一个人可以完成这些步骤；PR 用来保存可审查的变更和证据，不要求虚构第二个审批人。

## 1. 谁决定什么

- 用户决定玩法、质量标准、方案方向，以及需要用户观看的动作和手机体验是否通过。
- 执行窗口负责一个明确任务，修改、测试并更新交接记录。
- 复查窗口或子代理阅读实际差异与证据，指出回归、范围遗漏和未证实结论。AI 复查不等于 GitHub 上另一位用户的批准。
- 同一工作目录同一时间只设一个主写入窗口。主写入窗口可以明确划分互不重叠的文件给子代理；共享文件由主窗口整合。独立任务使用不同 worktree，避免两个对话同时修改同一批文件。

窗口只是执行者，任务 ID、文件、提交和 PR 才是接续依据。窗口 3 换成窗口 4，继续同一个任务和分支，不重开一份计划。

## 2. 信息各放一处

| 入口 | 只负责什么 |
| --- | --- |
| [DEVELOPMENT-PLAN.md](DEVELOPMENT-PLAN.md) | P0–P5 的开发顺序、产品目标与验收标准 |
| [PROJECT-STATUS.md](PROJECT-STATUS.md) | 唯一当前状态入口：正在做什么、下一步、失败、交接信息及发布状态 |
| `docs/tasks/<任务ID>.md` | 本任务的目标、范围、依赖、验收方法；不重复维护一份实时进度 |
| 阶段检查点与 QA 文件 | 某次检查的可复现证据，注明日期、代码／资产指纹和局限 |
| GitHub Issue／PR | 问题入口和变更审查；链接上述文件，不复制整份总计划 |
| `AGENTS.md` | 长期协作规则，不存临时端口、哈希和任务进度 |

任务卡从 [模板](tasks/TEMPLATE.md) 建立。小修复可直接写 PR；跨窗口或跨多步的工作需要任务卡。Issue 可选，已有计划编号即可开始本地工作，不为填表而填表。

## 3. 分支与任务大小

- `main` 保持可发布。新任务采用 `fix/<任务ID>-<主题>`、`feat/<任务ID>-<主题>` 或 `docs/<主题>`。不另建长期 `develop`。
- 一个分支／PR 对应一个可以独立验收的结果，例如“修复后场击球右肘折叠”，不要把整个人物重建装进一个永远无法验收的 PR。父任务 P1-1 可拆为 P1-1A、P1-1B；子任务验收不自动勾选父任务。
- 一个任务跨多个窗口继续用原分支和 worktree；不同任务分别建 worktree。依赖尚未合并的任务时记录依赖提交，不把叠加分支误称为来自干净 main。
- 开工先运行 `npm run project:brief`，核对 `git status`、分支、标签、所有 worktree 和远端。`origin/main` 只是本地缓存；联网用 `git ls-remote` 或 fetch 更新核对。离线明确记录验证范围。
- 对已核验的干净基线，新任务可执行 `git worktree add -b fix/P1-1A-elbow .cindy-worktrees/p1-1a origin/main`。这是示例；若任务依赖本地未提交人物成果，必须先保存并形成可继承的提交，不能直接使用这条命令丢掉依赖。
- 工作中允许小步 WIP 提交；检查失败要写在提交／PR／状态里。显式 `git add <文件>`，禁止把整目录、模型缓存、其他任务成果一起暂存。发布前整理范围，通常 squash merge。已共享分支优先追加修正，不随意 force-push。

## 4. PR 与验收

PR 写明：解决什么具体问题、改后行为、对应任务、测试证据、剩余失败、回退办法。未验收保持 Draft；一次完成多处相关拼写修正可共用一个 PR。

合并条件：

1. 差异只包含本任务，最新主线功能仍存在，依赖和来源许可明确。
2. 相关回归通过；最终候选运行完整 `npm test` 和 `npm run build`。已有失败也必须明确处理，不能因为“原来就失败”而自动放行，不能降门槛换绿灯。
3. 涉及人物、动作、击球、移动、回位和手机交互，按开发计划中对应场景验收。实际运行姿态、正常速度观感和手机实测不能被单元测试替代。
4. 本地预览写明服务目录和代码／资产版本；源码更新后重启快照服务，浏览器核验资源及 Service Worker 状态。
5. 审查意见处理完；需要用户视觉或玩法验收的结果已经用户确认。按已有会话授权执行后续操作，不因换窗口重复索要同一许可。

现有 CI 已在 push／PR 上执行 Node 22、24 的测试与构建。建议在 GitHub 的 main 规则中要求 PR、这两个实际检查和讨论解决，禁止强推／删除；单人仓库所需批准人数设为 0，不设置无法满足的自批要求。仓库拥有者仍需遵守流程，规则不能代替质量判断。**这些是配置建议，文件落地不表示远端分支保护已经启用。**

## 5. 合并与发布是怎样关联的

现有 `.github/workflows/pages.yml` 在 main 更新后触发 Pages 发布；部署文档记载 Vercel 生产跟踪 main，实施发布前还要核对实时设置。因此当前应把“合并 main”当作可能触发生产发布的动作。未通过验收的试验保留在分支和隔离预览。

**版本号仅在功能完成并准备上线时确定。** 规划、开发、修复、任务拆分和未验收 PR 阶段均不预定或递增发布版本号，也不把每次修改计划当成一个发布批次。开发进度用任务编号、提交和资源／构建指纹区分；基线依据远端进展、提交继承关系与实际功能核验，不用预定版本号或页面版本号代替。

确定版本号的门槛是：功能完成、相关测试及必要的用户视觉／玩法验收通过、发布范围冻结，并已进入上线准备。届时按当时最新已发布版本和整批实际改动判断：小修复递增补丁位，较大功能或体验更新递增次版本位，近乎全面重构或不兼容整体改版才递增主版本位。纯流程文档或内部工具不自动改游戏版本。版本文件、页面、发布文档和标签在该阶段统一核对；功能或发布范围再次变化时，先重新验收，再复核版本，不按计划修改次数连续加号。

发布后分别记录源码提交、构建部署结果和线上浏览器实读结果；只推送成功不能写成线上更新成功。发现线上问题优先用可审查的 revert／修复提交，避免重写 main 历史。

## 6. 切换对话窗口

不要等对话耗尽才留档。每完成一个可检查的小步骤、改换路线、发现新失败或准备切窗时，更新 `PROJECT-STATUS.md` 的 `activeTask` 和 `handoff`；保存文件及当前证据。关键字段如下：

| 字段 | 记录内容 |
| --- | --- |
| `baseline` | 已核验提交及历史来源分支，不是假定的当前最新提交；允许是当前 HEAD 的祖先。新建任务分支只需更新当前 `handoff.branch`，不得伪改历史来源 |
| `activeTask` | 目标范围、明确下一步、当前失败／外部依赖 |
| `handoff.taskId/taskFile/checkpoint` | 任务编号、任务卡、一个相关检查点 |
| `handoff.worktree/branch` | 实际目录与分支，移动目录或换机器后重新核验并更新 |
| `handoff.phase/stopReason` | 进行中／待复查／待验收／已合并；具体停在哪一步 |
| `handoff.validation` | 最近检查对应的提交或文件指纹、结果与证据位置，明确历史结果 |
| `handoff.scopeBoundary` | 已有授权范围及仍需决定的事项，不把计划当新增授权 |

旧窗口交接：

1. 停止向当前工作目录写入，确认子代理和长任务是否仍在运行；必要服务的目录和状态写入当前状态。完成可恢复提交，或明确保留未提交文件及备份位置。WIP 提交本身不会备份被忽略的源资产。
2. 执行 `npm run project:handoff -- --check`。错误必须修正；警告逐条核对。通过只表示本地交接信息一致，不表示运动质量通过。
3. 执行 `npm run project:handoff`，把输出交给新窗口；也可在新窗口直接指定同一工作目录和任务 ID。旧窗口停止继续修改。

新窗口第一条可直接用：

> 继续本项目当前任务。先运行 npm run project:brief 和 npm run project:handoff -- --check，读取 PROJECT-STATUS、输出中的任务卡和检查点，核对实际 Git 与远端进展；保留未提交成果，按记录的下一步继续，不重新从头制定人物计划。

突然中断时，以最后落盘记录和实际差异恢复；若旧窗口或后台任务仍在写入，先协调写入归属。交接命令只读本地文件，不联网、不提交、不修改分支、不备份、不判断旧窗口是否停止。它能发现目录／分支／提交继承错误、冲突及必需信息缺失；无法判断人写的“下一步”是否过时。

同机接续可利用当前目录。跨机器或重新 clone，必须已提交并推送必要源码、任务文档，并另外保存 `.blend`、动捕原始数据及 QA 等被忽略文件的可取回位置和哈希。不能只凭聊天摘要或一份交接文本承诺完整恢复。

## 7. 从已有在制成果迁移

若 main 上已有大量未提交成果，先处理这些依赖再执行新流程：

1. 记录 Git 状态；完整保存 tracked 二进制补丁、untracked 文件和必要 ignored 源资产，回读校验。单纯 stash 或 `git bundle` 均不等于三类文件都已保存。
2. 在原工作目录新建 `wip/<任务>` 分支，保留当前文件与预览关系；核对关键文件哈希和功能未变。禁止 reset／clean 掩盖混杂状态。
3. 按流程基础、场景工具、候选人物和运行时等实际依赖分组提交；必要时先保留一个明确标为未验收的本地 WIP 快照，再逐步整理。大型原始资产另存清单，不能直接塞入公开仓库。
4. 形成可继承提交后，新任务才从正确基线建立独立 worktree。未通过的实验成果不合并 main；可发布的小修复单独验证。

流程文件的首次落地可以在保留既有成果的目录完成；这不代表历史在制成果已经迁移或提交。实际迁移状态只看 PROJECT-STATUS 和 Git。
